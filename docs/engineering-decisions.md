# 关键技术决策

这份文档用于回答面试中的“为什么”，不是罗列技术栈。

## 为什么使用 LangGraph，而不是一个循环不断调用 LLM

Agent 包含检索、工具调用、审批、恢复和结束等不同状态。StateGraph 把节点、条件边与
共享状态显式化，并能通过 Checkpoint 恢复中断执行。代价是状态 Schema、消息配对和
恢复逻辑更复杂；如果任务只是一次问答，普通函数链更合适。

## 为什么 Checkpoint 和长期记忆要分开

Checkpoint 保存“一次图执行走到了哪里”，用于恢复中断；长期记忆保存跨轮次可复用的
用户信息。把两者混在一起，会让执行细节污染长期记忆，也难以分别设置保留周期。

## 为什么安全规则不能只写在 Prompt 里

Prompt 是给模型的行为建议，不是强制访问控制。项目用 Tool Policy 在代码层标记副作用、
重放策略和审批要求；未声明的 Tool Fail-Closed。这样即使模型路由错误，也不能直接绕过
执行门禁。

## 为什么 HITL 要放在 Tool 执行前

审批的目标是阻止副作用发生。若先执行再让用户确认，只能做事后通知。Approval Gate
先保存待审批信息并中断图；收到决定后从 Checkpoint 恢复，批准才执行，拒绝则生成合法
结果继续收尾。

## 为什么使用 BM25、Dense、RRF 和 Reranker

- BM25 擅长精确关键词、代码名和专有名词。
- Dense Retrieval 擅长语义相近但措辞不同的问题。
- RRF 用排名而非原始分数融合两路结果，避免不同评分尺度难以直接比较。
- Cross-Encoder 对候选集合做更精细的 query-document 联合打分，但成本更高，所以只
  用于 Top-N，而不是扫描全库。

这不是“模型越多越好”。每增加一路检索都要用标注问题比较 Recall@K、MRR、nDCG、
延迟和成本，证明它带来净收益。

## 为什么本地版本使用 SQLite

SQLite 部署简单、数据可检查，适合单机个人项目验证 Checkpoint、事件和策略持久化。
它不是多实例服务的最终方案；水平扩容时应迁移到支持并发、连接池、备份和权限治理的
数据库，并重新设计锁与任务租约。

## 为什么使用 SSE

这里主要是服务端持续向浏览器推送 Agent 状态，客户端不需要在同一连接上双向发送，
因此 SSE 比 WebSocket 更简单。当前进程内事件通道适合单机；多实例和断线续传需要持久
事件流、事件 ID 与 Last-Event-ID 机制。

## 为什么要同时做契约测试和 E2E Benchmark

契约测试使用 Fake Runtime，稳定验证 HTTP 状态码、Schema、会话隔离、SSE 与 HITL
控制流；E2E Benchmark 调真实模型，检查工具路由、检索决策、记忆和恢复。前者可重复但
不能证明模型行为，后者更真实但受模型、网络和数据漂移影响，所以两者不能互相替代。
